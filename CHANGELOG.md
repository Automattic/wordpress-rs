## [Unreleased]

### Added

- WordPress.com Reader tag streams: `GET /wpcom/v2/read/tags/{tag}/posts` returns `ReaderTagPostsResponse`, a page of a tag's `ReaderPost`s with the `next_page_handle` for the next page, and `unreadable_posts` for any post on the page that couldn't be read. `ReaderTagPostsParams` takes `number`, `page_handle`, `sort` (`ReaderTagPostsSort::Date` or `Popularity`), `before` and `after`. The API returns 10 posts at most. Swift gets it through `WPComApiClient.readerPosts.tagPosts`.
- `wp_com_e2e` has a `reader_sweep` binary, which runs the Reader endpoints against a large amount of real WordPress.com data and checks that every response, and every post in it, can be read. It's a test tool: nothing in the library changes.
- `ReaderStreamParams.fields` asks the Following, site and feed streams for only some fields of each post, such as `ID,site_ID,date`, which makes a page much smaller.
- The cache can keep Reader data for a reader who isn't signed in to WordPress.com. `ReaderOwner` is who Reader data belongs to, an account or `SignedOut`, and `WpApiCache::remove_reader_data` deletes what's cached for one.
- The cache can keep any Reader stream, not only the saved list. A stream ordered by date merges each page into what it has, removes posts the server no longer returns, and marks a gap where a refresh didn't reach the posts it already had. A stream kept in the server's order swaps its posts when its first page arrives. A new `reader_unreadable_posts` table keeps the IDs of posts a page couldn't read.
- `ReaderService` is the entry point to a reader's Reader, for an account or for a reader who isn't signed in. `ReaderService::stream` gives a `ReaderStreamCollection` for a `ReaderStream` (Following, a site's, a feed's or a tag's posts), read from the cache: `load_items` returns the cached posts without touching the network, `refresh` merges the first page into them, `load_more` loads the next page, and `fill_gap` loads the posts a refresh skipped. A post a page couldn't read is counted in `ReaderStreamInfo.unreadable_post_count` and kept by its IDs.
- Saved posts work for a reader who isn't signed in. `ReaderSavedService::for_reader` with `ReaderOwner::SignedOut` keeps saves on the device and sends nothing, and `ReaderService::saved` gives the reader's saved posts either way. After sign-in, `ReaderSavedService::adopt_signed_out_saves` moves those saves to the account.
- WordPress.com Reader seen status: `POST /wpcom/v2/seen-posts/seen/blog/new` and `/delete` mark a site's posts as seen or unseen, and `POST /wpcom/v2/seen-posts/seen/new` and `/delete` do the same for an RSS feed's posts. Swift gets them through `WPComApiClient.readerSeen`.
- WordPress.com Reader blocked sites: `GET /wpcom/v2/me/blocks/sites` lists the sites the user blocked, and `POST /rest/v1.1/me/block/sites/{site}/new` and `/delete` block and unblock one. Swift gets them through `WPComApiClient.readerBlocks`.
- The Reader keeps what the user turns on or off, such as a post marked as seen or a blocked site, on the device first. `ReaderService::set_post_seen` and `set_site_blocked` show the change straight away, send it, and put it back if the server refuses. Offline, the change waits, and `sync_actions` sends it later. A blocked site's posts are left out of every stream. `set_user_blocked` blocks a user on this device, since WordPress.com keeps no such list.
- `ReaderService::post_opened` counts a view when a post is opened in the Reader, and decides whether it counts: not for an RSS post, and not for a member of a public site. `ReaderPageView` builds the request for an app that sends it itself. `ReaderService::cached_post` reads a post from the cache with its content.
- Four more WordPress.com Reader streams, each returning `ReaderPostsResponse` and paging by date with `before`: `GET /rest/v1.2/read/liked` (the posts the user liked, ordered by `ReaderPost.date_liked`), `/read/a8c` (Automattic's posts), `/read/following/p2` (the P2s the user follows) and `/freshly-pressed` (the posts WordPress.com's editors picked, ordered by the new `ReaderPost.editorial_displayed_on`). For the next page, pass the page's `date_range.after` as `before`. `ReaderLikedPostsParams`, `ReaderOrganizationPostsParams` and `ReaderFreshlyPressedParams` take each stream's own parameters, and `ReaderStreamOrder` is the `order` some of them take. Freshly Pressed answers without an account. Swift gets them through `WPComApiClient.readerPosts.liked`, `.automattic`, `.followingP2` and `.freshlyPressed`.
- WordPress.com Reader search: `GET /rest/v1.2/read/search` returns `ReaderSearchPostsResponse`, a page of `ReaderSearchPost`s (a `ReaderPost` with its `score`, `site_follower_count` and `date_added`) and the `next_page_handle` for the next page. `ReaderSearchPostsParams` takes `q`, `sort` (`ReaderSearchSort::Relevance` or `Date`), `number`, `page_handle`, `offset`, `before`, `after`, `lang`, `algorithm`, `meta` and `fields`. The API returns 20 posts a page at most, and 200 results at most when sorted by relevance. It answers without an account. Swift gets it through `WPComApiClient.readerPosts.search`.
- A WordPress.com Reader list's posts: `GET /rest/v1.3/read/list/{owner}/{slug}/posts` returns `ReaderListPostsResponse`, a page of the list's `ReaderPost`s with the `next_page_handle` for the next page, `unreadable_posts`, and `missing_posts` for the cards the API sent without a post. `ReaderListOwner` and `ReaderListSlug` name the list. A public list answers without an account. Swift gets it through `WPComApiClient.readerPosts.listPosts`.
- WordPress.com Reader streams of cards: `GET /wpcom/v2/read/streams/discover` (Discover's recommended posts) returns `ReaderDiscoverResponse`, and `/read/streams/first-posts` (new sites' first posts) returns `ReaderFirstPostsResponse`. Each is a page of `ReaderCard`s with the `next_page_handle` for the next page. A card is a `Post`, `RecommendedSites`, `NewSites` or `SuggestedTags`; a card of a kind the library doesn't know is `Unknown` with its type name, and one that can't be read is listed in `unreadable_cards` without failing the page. Both answer without an account. Swift gets them through `WPComApiClient.readerPosts.discover` and `.firstPosts`.
- `GET /wpcom/v2/read/tags/posts` returns the posts of several tags as a `ReaderTagPostsResponse`. `ReaderTagsPostsParams` takes the `tags`, `number`, `page_handle`, `page`, `sort`, `before` and `after`. Swift gets it through `WPComApiClient.readerPosts.tagsPosts`.
- `ReaderTagPostsParams.page` pages a tag's posts by page number. It's the only way to page posts sorted by popularity: the API answers a `page_handle` from that order with the first page again.
- WordPress.com Reader single posts: `GET /rest/v1.2/read/sites/{site}/posts/{post}` and `GET /rest/v1.3/read/feed/{feed}/posts/{item}` return one `ReaderPost`, in the shape the streams send, and `GET /rest/v1.2/read/site/{site}/post/{post}/related` returns `ReaderRelatedPostsResponse`, the posts related to a post, from the same site and from others. `GET /rest/v1.1/sites/{site}/posts/slug:{slug}` finds a post by its slug and returns `ReaderPostBySlug`, which has the post's IDs to fetch it with: it comes from the general posts endpoint, so it isn't a `ReaderPost`. All four answer signed out for a public site. Swift gets them through `WPComApiClient.readerPost`.
- WordPress.com Reader URL resolving: `GET /wpcom/v2/mobile/resolve-reader-url` takes a post's address and returns `ReaderResolvedUrl`, the site and post IDs to fetch it with. It resolves a post of a WordPress.com or Jetpack site, including one on the site's own domain, and needs a signed-in user. An address that isn't a post's is a `post_not_found` error. Swift gets it through `WPComApiClient.readerPost.resolveUrl`.
- `ReaderStream` has nine more streams: `Liked`, `Automattic`, `P2`, `FreshlyPressed`, `Tags`, `Search`, `ReaderList`, `Discover` and `FirstPosts`. Each is cached and paged like the first four. `ReaderStreamCollection::load_cards` returns the cards a stream has among its posts that aren't posts, such as Discover's recommended sites, each with the post it comes after.
- WordPress.com Reader menu and tags: `GET /rest/v1.3/read/menu` returns `ReaderMenu`, the Reader's streams, the tags the user follows and the tags to suggest, each a `ReaderMenuItem` with a `ReaderMenuItemKind` (`Stream`, `Tag`, `List`, `Organization`, or `Other` for a kind this version doesn't know). `GET /rest/v1.2/read/tags/{slug}` returns a `ReaderTag`, and `GET /wpcom/v2/read/interests` the `ReaderInterest`s a new reader picks from. All three answer signed out: the menu then has only Discover and the suggested tags. A tag's slug is percent-decoded as it's read, so a slug that isn't ASCII can be passed back as a `ReaderTagSlug`. Swift gets them through `WPComApiClient.readerTags`.
- WordPress.com Reader subscriptions: `GET /rest/v1.2/read/following/mine` returns `ReaderSubscriptionsResponse`, a page of the sites and feeds the user is subscribed to, newest first. Each `ReaderSubscription` has its own ID, the site's `blog_id` (`None` for a feed with no WordPress.com site), its `feed_id`, and its `delivery_methods`: whether posts and comments are emailed and how often (`ReaderSubscriptionEmailFrequency`), and whether posts send a notification. `ReaderSubscriptionsParams` takes `page`, `number`, `q`, `filter` and `meta`. The list pages by page number, and a short or empty page isn't the end, so `ReaderSubscriptionsResponse::has_next_page` says when to stop. `GET /rest/v1.1/sites/{site}/follows/mine` returns a `ReaderSiteFollowStatus`. Both need a token. Swift gets them through `WPComApiClient.readerSubscriptions`.
- WordPress.com Reader post likes: `GET /rest/v1.2/sites/{site}/posts/{post}/likes` returns `ReaderLikesResponse`, a page of the users who liked a post, newest like first, with `found` and `i_like`. Each `ReaderLike` is the user and their `date_liked`. `ReaderLikesParams` takes `number` (90 at most), `before` and `exclude`. The list pages by the date of the last like, and `ReaderLikesResponse::next_page_params` returns the parameters for the next page, or `None` on the last. It answers signed out. Swift gets it through `WPComApiClient.readerLikes`.
- WordPress.com Reader comments: `GET /rest/v1.1/sites/{site}/posts/{post}/replies` returns `ReaderCommentsResponse`, a page of a post's `ReaderComment`s with `found`, and `unreadable_comments` for any that couldn't be read. A comment has its `parent_id`, `ReaderCommentAuthor`, `date`, `content` and `raw_content`, `ReaderCommentStatus`, `ReaderCommentType`, `like_count` and `i_like`. `ReaderCommentsParams` takes `number` (100 at most), `offset`, `page`, `order`, `hierarchical`, `after`, `before`, `comment_type`, `status`, `author_wpcom_data`, `force` and `fields`. Pass `force: "wpcom"` for a Jetpack site, whose comments otherwise arrive without likes. `GET /rest/v1.2/sites/{site}/comments/{comment}/likes` returns the users who liked a comment as a `ReaderLikesResponse`, and `GET /rest/v1.1/sites/{site}/posts/{post}/subscribers/mine` a `ReaderPostCommentsSubscription`, which needs a token. Swift gets them through `WPComApiClient.readerComments` and `WPComApiClient.readerLikes.commentLikes`.
- WordPress.com Reader sites and feeds: `GET /rest/v1.2/read/sites/{site}` returns `ReaderSite`, a site's Reader info, including whether the user follows it and, in `delivery_methods`, how they're sent its new posts. `GET /rest/v1.1/read/feed/{feed}` returns `ReaderFeed`, a feed's. `ReaderSite.feed_id` and `ReaderFeed.site_id` link the two, and each is `None` when there's no counterpart. `GET /rest/v1.1/read/feed` searches sites and feeds with `q`, or finds the feeds at an address with `url`, and returns `ReaderFeedSearchResponse`, whose `next_offset` or `next_page_handle` asks for the next page. All three answer signed out, with nothing about the user. Swift gets them through `WPComApiClient.readerSites`.
- WordPress.com Reader user profiles: `GET /rest/v1.1/users/{user}` returns `ReaderUserProfile`, a user's public profile: their names, description, avatar and main site. The user is a `WpComUserIdentifier`, a login or an ID. The API reads a number as a login first, so an ID that is also someone's login finds that user instead. It needs a signed-in user. Swift gets it through `WPComApiClient.readerUsers.profile`.
- `ReaderService::fetch_post` fetches one post by its IDs and keeps it in the cache, `fetch_post_by_slug` finds it by its slug, and `fetch_post_at_url` by its address. `ReaderStream::Related` is the posts related to a post. A stream asks again, an hour later, for posts its pages couldn't read, and `ReaderStreamCollection::retry_unreadable_posts` does it on request.
- What a Reader post's card shows is worked out one way for both apps, which until now each had their own rules. `reader_post_summary` gives the card's summary as plain text, from the excerpt or, without one, the content. `reader_post_reading_time_minutes` gives the reading time, at 200 words a minute, from `word_count` or, for the streams that don't send it, by counting the words in the content. `reader_post_card_type` gives the layout, a `ReaderPostCardType`: `Default`, `Photo`, `Gallery`, `Video` or `CrossPost`. `reader_post_gallery_image_urls` lists the images a gallery card shows. Each function's documentation says where the iOS app, the Android app and the web Reader differ, and which it follows.
- `ReaderPostRecord` has a post's `summary`, `reading_time_minutes` and `card_type`, worked out once when the post is stored, so both apps show the same.
- Liking a WordPress.com Reader post: `POST /rest/v1.1/sites/{site}/posts/{post}/likes/new` likes a post for the user and `/likes/mine/delete` removes the like. Both return `ReaderPostLikeResponse`, with `success`, whether the user likes the post now (`i_like`), its `like_count`, and the user as `liker`. Unliking a post the user doesn't like is a 200 with `success: false`. Swift gets them through `WPComApiClient.readerLikes.likePost` and `.unlikePost`.
- Liking a comment on a WordPress.com Reader post: `POST /rest/v1.1/sites/{site}/comments/{comment}/likes/new` likes a comment for the user and `/likes/mine/delete` removes the like. Both return `ReaderCommentLikeResponse`, with `success`, whether the user likes the comment now (`i_like`), and its `like_count`. Unliking a comment the user doesn't like is a 200 with `success: false`. Swift gets them through `WPComApiClient.readerLikes.likeComment` and `.unlikeComment`.
- Following and unfollowing in the WordPress.com Reader. By site ID: `POST /rest/v1.1/sites/{site}/follows/new` and `/follows/mine/delete` return `ReaderFollowSiteResponse`, with `is_following`. By address, which also follows an RSS feed: `POST /rest/v1.1/read/following/mine/new` takes `ReaderFollowUrlParams` (`url`, `source`) and returns `ReaderFollowUrlResponse`, with the new `ReaderSubscription`, or `subscribed: false` and an `info` of `invalid_feed` for an address with no feed. `POST /rest/v1.1/read/following/mine/delete` takes `ReaderUnfollowUrlParams` (`sub_id` or `url`, `blog_id`, `email_id`) and returns `ReaderUnfollowUrlResponse`. Swift gets them through `WPComApiClient.readerSubscriptions.followSite`, `.unfollowSite`, `.followUrl` and `.unfollowUrl`.
- A WordPress.com Reader subscription's delivery settings: `POST /rest/v1.2/read/site/{site}/post_email_subscriptions/new` and `/delete` start and stop the emails of a site's new posts, and `/update` changes how often they're sent, with `ReaderPostEmailFrequencyParams`. All three return `ReaderPostEmailSubscriptionResponse`. `POST /rest/v1.2/read/site/{site}/comment_email_subscriptions/new` and `/delete` do the same for the emails of new comments, and return `ReaderCommentEmailSubscriptionResponse`. `POST /wpcom/v2/read/sites/{site}/notification-subscriptions/new` and `/delete` turn notifications of new posts on and off, and return `ReaderNotificationSubscriptionResponse`. Each answer's `subscribed` says what's on now. Swift gets them through `WPComApiClient.readerSubscriptions`, as `subscribeToPostEmails`, `unsubscribeFromPostEmails`, `updatePostEmails`, `subscribeToCommentEmails`, `unsubscribeFromCommentEmails`, `subscribeToNotifications` and `unsubscribeFromNotifications`.
- Following tags in the WordPress.com Reader: `POST /rest/v1.2/read/tags/mine/new` follows the tags in `ReaderFollowTagsParams` and returns `ReaderFollowTagsResponse`, with the IDs it added in `added_tags`. `POST /rest/v1.1/read/tags/{slug}/mine/delete` unfollows a tag and returns `ReaderUnfollowTagResponse`, with the ID it removed in `removed_tag`. Both answers list every tag the user now follows as `ReaderTag`s, and any that couldn't be read in `unreadable_tags`. Following a tag the user already follows is a 200 that adds none, and unfollowing one they don't follow is a `not_subscribed` error. Swift gets them through `WPComApiClient.readerTags.followTags` and `.unfollowTag`.
- The cache keeps the Reader menu with the tags a reader follows, the sites and feeds an account follows with their delivery settings, what the Reader shows of a site or feed besides its posts, and posts' comments, including comments written on the device that the server hasn't taken yet (migrations 0021 and 0022).
- Writing comments in the WordPress.com Reader: `POST /rest/v1.1/sites/{site}/posts/{post}/replies/new` adds a comment to a post and `POST /rest/v1.1/sites/{site}/comments/{comment}/replies/new` replies to one. Both take `ReaderNewCommentParams` and return the new `ReaderComment`. `POST /rest/v1.1/sites/{site}/posts/{post}/subscribers/new` and `/subscribers/mine/delete` subscribe the user to a post's comments and unsubscribe them, returning `ReaderPostCommentsSubscriptionResponse`, and `/subscribers/mine/update` turns the subscription's notifications on or off with `ReaderCommentsNotificationsParams`, returning the `ReaderPostCommentsSubscription`. Swift gets them through `WPComApiClient.readerComments`, as `newComment`, `newReply`, `subscribe`, `unsubscribe` and `updateSubscription`.
- `ReaderService` likes posts and comments, follows sites, feeds and tags, and changes a followed site's delivery settings: `set_post_liked`, `set_comment_liked`, `set_followed`, `set_tag_followed`, `set_post_emails`, `set_comment_emails`, `set_post_notifications`, `set_comments_subscribed` and `set_comment_notifications`. Each shows straight away, is sent, and is put back if the server refuses. A signed-out reader follows tags on the device, and `adopt_signed_out_tags` moves them to an account.
- `ReaderService` keeps the Reader menu (`refresh_menu`, `menu`, `followed_tags`), the account's subscriptions (`refresh_subscriptions`, `subscriptions`) and what it shows of a site or feed (`fetch_site`, `fetch_feed`, `cached_site`) in the cache, and passes on `search_sites`, `interests`, `tag_info`, `user_profile`, `post_likes` and `comment_likes`.
- `ReaderService::comments` gives a post's comments from the cache as a `ReaderCommentsCollection`. `post_comment` writes a comment or a reply: it shows at once, is sent once, and stays as not taken if that fails, until `retry_comment` or `discard_comment`.
- Swift: `WPComApiClient.makeReaderService(cache:owner:savedSource:)` creates the `ReaderService` for an account, or for a reader who isn't signed in.
- The saved list can be sorted: `ReaderSavedPostsParams` has `order_by`, a `ReaderSavedOrderBy` (when each post was saved, or when it was published), and `order`. The API reads `order` only in capitals, which is how it is sent.
- `reader_post_content_image_urls` lists the images in a Reader post's content, for storing them so the post can be read with no connection. It leaves out tracking pixels, which would count a view when fetched. `reader_post_content_with_stored_images` returns the content with each stored image pointing at its copy.
- The cache keeps what the device has of each saved Reader post for reading with no connection: whether its content was fetched, why a fetch failed, and which of its images are stored as files. `ReaderSavedRepository::select_list_ordered` reads the saved list by when each post was saved or published, newest or oldest first.
- `ReaderSavedService::download_for_offline` gets every saved Reader post ready to read with no connection. It fetches the content of each save that has none, from the saved list and then one post at a time, and reports what the device has. Each `ReaderSavedListItem` has an `offline` state: not downloaded, downloading, ready, or failed with the reason. `retry_offline` tries a failed one again.
- Saved Reader posts can keep their images on the device. `ReaderSavedService::set_offline_image_store` says where, and how much room they may take, and `download_for_offline(include_images: true)` stores them, newest save first. When room runs out, the oldest saves lose their images and keep their text. Unsaving a post deletes its images. `offline_post` returns a saved post with its content pointing at the stored copies.
- `ReaderSavedService::saved_posts_ordered` gives the saved list by when each post was saved or published, newest or oldest first. Each order loads its own pages.
- Swift: `ReaderPostRecord.galleryImageURLs` and `contentImageURLs` give the images of a Reader post's content.
- `wp_com_e2e` has two trials that write to WordPress.com through the Reader service: one writes a comment and a reply and deletes both, and one counts a view of a post. They run only against a site the account owns, named in `WP_COM_E2E_OWN_SITE_ID`, and are skipped without it.
- `Documentation/adding-a-wordpress-com-endpoint.md` is the recipe for adding a WordPress.com endpoint: choosing the version, finding its parameters, modelling from recorded responses, the tests it needs, and the Swift and Kotlin checks.
- The Kotlin example app has Reader screens, built on `ReaderService`, for a WordPress.com account and for a reader who isn't signed in: a Reader home (the menu's streams and lists, followed and recommended tags, a search of posts, and a site's or a feed's stream by its ID), a stream with its cards and its gaps, a post, its comments, the subscriptions with their delivery settings, the blocked sites, a search of sites, and the saved posts. Each shows what the cache has, then fetches, and reloads when the cache changes. The signed-out Reader opens from the app's first screen, and an account's from its WordPress.com screen.
- The Kotlin example app has an offline reading screen for the Reader. It downloads the saved posts' text, and their images into a folder with a size limit, shows what the device has of each saved post, sorts the list four ways, and opens a saved post from the device with its stored images.
- The Swift example app has a Reader tab that uses the whole of `ReaderService`. It works without a WordPress.com account, as the reader who isn't signed in, and as the account when the app has one. It has a home screen (the menu's streams and lists, followed and recommended tags, search, a site's or a feed's stream by ID, a post by its slug or address, and the actions waiting to be sent, with a "Sync" button), a screen for any stream (posts, cards, gaps, unreadable posts, and a menu on each post to like, save, mark as seen, follow and block), and screens for a post, its comments, who liked it, the account's subscriptions and their delivery settings, blocked sites, and the search that finds sites. Every screen shows the cache first and reloads when the cache changes. A "Simulate no connection" switch, and the `-reader-offline` launch argument, make every Reader request fail as it does offline. The saved posts screen now uses `ReaderService::saved`, so it works signed out too, and there is one Reader cache. `scripts/example-app-ui-script.sh` runs a script of taps against the app on an iOS Simulator and saves screenshots: see `Documentation/local-development.md`.
- The Swift example app has an offline reading screen for the Reader. It downloads the saved posts' text, and their images into a folder with a size limit, shows what the device has of each saved post, sorts the list four ways, and opens a saved post from the device with its stored images.
- `reader_error_message` and `reader_saved_error_message` give a Reader error's sentence to Swift and Kotlin, which otherwise only get its case and fields. In Swift they are `ReaderError.message` and `ReaderSavedError.message`.
- `ReaderStreamItem.is_saved` says whether each post of a stream is saved, so an app no longer asks for each post. `ReaderSavedService::pending_count` counts the saves and unsaves the server doesn't have yet.
- `reader_stream_for_menu_item` gives the stream a Reader menu entry opens, including a list's, whose owner and slug are only in its address. `reader_likes_next_page_params` gives Swift and Kotlin the next page of likes. `reader_data_is_relevant_update` says whether a change to the cache is one that the menu, the subscriptions, the blocks, what's waiting to be sent, a post or a site shows.
- Swift exports `UpdateHook`, `DbTable` and `HookAction` from `WordPressApiCache`, whose own methods use them. Kotlin's `WpComApiClient.makeReaderService` creates the Reader service.
- `wp_com_e2e` has a trial that likes a post through the Reader service and puts it back. It runs only against a site the account owns, named in `WP_COM_E2E_OWN_SITE_ID`.
- `scripts/example-app-adb-script.py` drives the Kotlin example app on an Android emulator or device from a script of steps, and saves a screenshot and a list of what's on screen where the script asks, as `scripts/example-app-ui-script.sh` does for the Swift app. Scripts for the Reader signed out and for offline reading come with each app.
- `Documentation/reader-endpoints.md` lists every WordPress.com Reader endpoint the library calls, with the parameters it sends and how they compare with WordPress.com's public documentation. `scripts/reader-endpoints-doc.py` regenerates it from the code comments, and its `--check` fails when the document is out of date.
- `wp_com_e2e` reads the server back after each write of its Reader service trials on the account's own site: a post like, a comment like, a comment subscription and its notifications, a followed site's emails and notifications, and a follow by site ID. Each trial checks that the server has the change, then that it has it put back.
- A unit test covers a Reader comment that the server takes on `ReaderCommentsCollection::retry_comment`: it adds one to the cached post's comment count, as one taken first time does, and a send the server doesn't take adds nothing.
- `ReaderService::resolve_link` finds what a link opens in the Reader: `ReaderLink::Post` (fetched and cached), `Site` or `Feed` (their details cached, to open their stream), or `NotInReader` with a `ReaderLinkNotInReader` reason: not a web address, a `wp.me` short link, nothing at that address, or not a WordPress.com or Jetpack site and no feed. `reader_link_not_in_reader_message` says the reason in words. A site's home address works signed out; any other address needs an account, since the server only resolves a post with a token. It replaces `fetch_post_at_url`, and both example apps open a site or feed link as its stream, and say why when a link opens nothing.
- `reader_sweep` walks every Reader stream: Liked, Automattic, P2, Freshly Pressed, several tags' posts, search, a list's posts, Discover and first posts, each paged as the library pages it. It counts each kind of card a stream of cards sends, reports a kind the library doesn't know, and works out each post's summary, reading time and card type. It's a test tool: nothing in the library changes.
- `wp_com_e2e` fetches a Jetpack site's post and a VIP site's post through the site's and the feed's single-post endpoints, and checks the fields that tell each kind apart. Anonymized fixtures of both kinds have unit tests. Nothing in the library changes.
- `wp_com_e2e` runs `ReaderService::resolve_link` against the live API: a post's address with an account, a site's and a feed-only site's home address, an address that is neither, and a post's address signed out, which sends nothing. Nothing in the library changes.
- `reader_sweep`'s check for a post with words but no summary or reading time only counts words a reader sees, leaving out CSS, scripts, attribute values and other hidden markup. It's a test tool: nothing in the library changes.

### Changed

- **Internal:** Disabled Dependabot updates for rusqlite to preserve compatibility with Apple's system SQLite on iOS 18.
- `ReaderPostRecord` keeps more of a Reader post: its short URL, author ID, cross-post, word count, the site's language and kind, and whether likes and comments are open, whether the user subscribed to its comments and whether they've seen it. Each new field has a default, so code that builds a record still compiles.
- `ReaderService::new` takes the app as `saved_source`, which is recorded with each save.
- `ReaderStreamOrder`, which says whether a stream's posts are ordered by date or kept in the server's order, is now `ReaderStreamOrdering`. The name is free for the `order` parameter of the streams added next.
- One saved post that can't be read no longer fails its page of the saved list. `ReaderSavedPostsResponse.posts` has the posts that could be read, and the new `unreadable_posts` lists the others with their IDs. Each is still saved.

- Swift: Large (>10 MB) multipart uploads leaked their temporary file. A form estimated over 10 MB (or built with `forceWriteToFile: true`) is serialized to a UUID-named temp file under `FileManager.default.temporaryDirectory` and handed to `URLSession.uploadTask(fromFile:)`, which treats the file as caller-owned — it reads it during the transfer but never deletes it — so every large media upload (4K video, ProRAW, multi-file posts) left a temp file behind for the OS to reclaim later. `upload(...)` now removes the file once the transfer completes, on success, failure, or cancellation. ([#1540](https://github.com/Automattic/wordpress-rs/issues/1540))
- A datetime WordPress never set (`0000-00-00 00:00:00`, and PHP's renderings of it) is no longer read as an instant in 1 BCE. Fields that can be unset now report it as absent; everywhere else it is a parse error rather than a plausible-looking date.
- A cached post or media item whose stored `modified_gmt` could not be read was treated as up to date and never refetched, so the stale copy stayed in the cache indefinitely. The staleness check dropped such rows silently, and a row missing from that lookup means "not stale"; an unreadable timestamp now marks the item stale instead.
- Swift: `WpRequestExecutor.sleep(millis:)` converted milliseconds to nanoseconds with the wrong factor (`* 1_000` instead of `* 1_000_000`), so it slept 1000× too short — a `Retry-After: 30` waited 30 ms instead of 30 s. `RetryAfterMiddleware` then re-sent immediately, the server kept returning 429, and after `max_retries` the caller observed `MisconfiguredRateLimitError` where honoring the backoff would usually have succeeded. The executor now waits the full interval, and no longer risks a `fatalError` if the sleep's task is cancelled.
- Swift: Classify invalid-SSL failures from the failed handshake's `SecTrust` (`URLError.failureURLPeerTrust`), via `SecTrustCopyCertificateChain`, instead of reading the undocumented `NSErrorPeerCertificateChainKey` `userInfo` string that has no public constant. Behavior is unchanged on every platform: iOS/macOS/tvOS still surface the presented certificate as `certificateNotValidForName`, and watchOS — which exposes no peer trust — still degrades to `genericSslError`. ([#1510](https://github.com/Automattic/wordpress-rs/issues/1510))
- `isSiteUnreachable` now returns the same answer for a refused connection — the host resolves, but nothing is listening (server down, wrong port) — on every executor. Previously it was `NonExistentSiteError` on Swift (so `isSiteUnreachable` was `true`) but the generic `HttpError` on Kotlin and reqwest (so it was `false`); a refused connection is now a `ConnectionError` everywhere, which `isSiteUnreachable` covers. `NonExistentSiteError` is reserved for a DNS-resolution failure.
- Swift multipart form and media uploads no longer crash when a file becomes unreadable while its body is being serialized. `MultipartForm` fed a failed `InputStream.read` — a `-1` return, e.g. the file was deleted after the upload started or a mid-read I/O error on an external / file-provider / iCloud-evicted volume — straight into `Data(bytesNoCopy:count:deallocator:)`, whose negative count traps. The read failure now surfaces as a `RequestExecutionFailed` error carrying the underlying stream error instead of trapping the process.
- **BREAKING:** The comment create endpoint now returns `CommentWithViewContext`, fixing a deserialization failure for users without `moderate_comments` (core returns them a view-context body). Callers that need edit-only fields off the create result must retrieve the comment with edit context instead.
- Swift multipart serialization also throws `inaccessibleFile` when a field's `InputStream` fails to *open* — e.g. the backing file was deleted between the field's construction and serialization — not only when a `read` fails mid-body. A failed `open()` leaves the stream in `.error` with `hasBytesAvailable == false`, so the read loop never runs and the mid-read `-1` guard can't fire; without a post-loop `streamStatus == .error` check, serialization emitted the closing CRLF and handed back a well-formed-but-empty part. `multipart/form-data` carries no per-part length, so the server couldn't detect the truncation and a should-fail upload became a silently-wrong one. ([#1542](https://github.com/Automattic/wordpress-rs/issues/1542))
- **BREAKING:** A rejected WordPress.com REST v1.x request now surfaces as `WpApiError::WpError` carrying the API's error code, instead of an opaque `UnknownError`. v1.x names the code field `error` rather than `code`, and only `code` was read. Callers matching `UnknownError` to detect these will need to match `WpError` instead.
