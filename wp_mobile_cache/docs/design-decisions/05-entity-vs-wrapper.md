# Design Decision 5: Entity vs Wrapper Types

> **Last Updated:** 2025-10-21

## Decision

Separate domain entities from database wrappers.

## Context

When storing WordPress data in the cache, we need to decide how to represent it:

```rust
// Option 1: Domain entity includes DB fields (rejected)
pub struct AnyPostWithEditContext {
    pub rowid: RowId,           // DB field
    pub db_site_id: DbSite,     // DB field
    pub id: PostId,             // WordPress field
    pub title: String,          // WordPress field
    // ...
}

// Option 2: Separate domain and wrapper (chosen)
pub struct AnyPostWithEditContext {
    pub id: PostId,             // WordPress field
    pub title: String,          // WordPress field
    // ... only WordPress fields
}

pub struct DbAnyPostWithEditContext {
    pub row_id: RowId,          // DB field
    pub site: DbSite,           // DB field
    pub post: AnyPostWithEditContext,  // Domain entity
    pub last_fetched_at: String,       // DB field
}
```

## Rationale

### Clean Domain Model

**`AnyPostWithEditContext` represents WordPress REST API structure:**

```rust
// Direct mapping to WordPress REST API response
pub struct AnyPostWithEditContext {
    pub id: PostId,
    pub title: PostTitleWithEditContext,
    pub content: PostContentWithEditContext,
    pub author: UserId,
    pub categories: Option<Vec<TermId>>,
    pub tags: Option<Vec<TermId>>,
    // ... matches API response exactly
}
```

**Benefits:**
- ✅ Can be used outside database context (API clients, serialization)
- ✅ No database coupling in domain model
- ✅ Easier to understand (pure WordPress data)
- ✅ Can be shared across crates without database dependency

### Database Wrapper Adds Metadata

**`DbAnyPostWithEditContext` includes cache-specific fields:**

```rust
pub struct DbAnyPostWithEditContext {
    pub row_id: RowId,          // SQLite's internal ID
    pub site: DbSite,            // Multi-site scope
    pub post: AnyPostWithEditContext,  // The WordPress post
    pub last_fetched_at: String, // When we cached it
}
```

**Benefits:**
- ✅ Provides access to database identifiers when needed
- ✅ Includes cache metadata (last_fetched_at)
- ✅ Wraps domain entity without modifying it
- ✅ Clear separation of concerns

### Repository Entity Type

**Repository uses domain model for insert operations:**

```rust
impl Repository for PostRepository {
    type Entity = AnyPostWithEditContext;  // Domain entity, not wrapper
}

impl PostRepository {
    // Insert takes domain entity
    pub fn upsert(
        &self,
        executor: &impl QueryExecutor,
        item: &AnyPostWithEditContext,  // Domain entity
        site: &DbSite,
    ) -> Result<RowId> {
        // Generate rowid and last_fetched_at during insert
    }
}
```

**Why?**
- Callers have WordPress data, not database wrapper
- rowid doesn't exist before insert
- last_fetched_at is generated by database

### Query Return Type

**Queries return wrapper to provide access to database metadata:**

```rust
impl PostRepository {
    pub fn select_by_rowid(
        &self,
        executor: &impl QueryExecutor,
        site: &DbSite,
        rowid: RowId,
    ) -> Result<DbAnyPostWithEditContext> {  // Wrapper type
        // ...
    }
}
```

**Usage:**
```rust
let db_post = repo.select_by_rowid(&conn, &site, rowid)?;

// Access database metadata
println!("RowID: {:?}", db_post.row_id);
println!("Cached: {}", db_post.last_fetched_at);

// Access domain entity
println!("Title: {}", db_post.post.title.raw);
println!("Author: {}", db_post.post.author);
```

## Example Usage

### Inserting Data

```rust
// Start with WordPress API response
let post = AnyPostWithEditContext {
    id: PostId(123),
    title: PostTitleWithEditContext { raw: "Hello".into() },
    // ... other WordPress fields
};

// Insert domain entity
let repo = PostRepository;
let rowid = repo.upsert(&conn, &post, &site)?;
// Database generates: rowid, last_fetched_at

// Later, query returns wrapper with metadata
let db_post = repo.select_by_rowid(&conn, &site, rowid)?;
assert_eq!(db_post.post.id, PostId(123));  // Domain entity
assert_eq!(db_post.row_id, rowid);          // Database metadata
```

### Using Wrapper Type

```rust
fn display_cached_post(db_post: &DbAnyPostWithEditContext) {
    // Access domain entity
    println!("Title: {}", db_post.post.title.raw);
    println!("Content: {}", db_post.post.content.raw);

    // Access cache metadata
    println!("Cached at: {}", db_post.last_fetched_at);
    println!("Database ID: {}", db_post.row_id.0);
}
```

### Unwrapping When DB Metadata Not Needed

```rust
let db_post = repo.select_by_post_id(&conn, &site, post_id)?;

// Extract domain entity when DB metadata not needed
let post: AnyPostWithEditContext = db_post.post;

// Send to API client, serialize, etc.
send_to_api(&post)?;
```

## Alternatives Considered

### Alternative 1: Domain Entity Includes DB Fields

```rust
pub struct AnyPostWithEditContext {
    pub rowid: Option<RowId>,  // Some after insert, None before
    pub db_site_id: Option<DbSite>,
    pub last_fetched_at: Option<String>,
    pub id: PostId,
    pub title: String,
    // ...
}
```

**Why rejected:**
- ❌ Confuses domain model with persistence
- ❌ Option fields are awkward (which should be Some/None?)
- ❌ Database coupling in domain type
- ❌ Cannot use outside database context cleanly
- ❌ WordPress API client would have irrelevant fields

### Alternative 2: Separate Types for Insert/Query

```rust
// For inserting
pub struct PostInsert {
    pub id: PostId,
    pub title: String,
    // ...
}

// For querying
pub struct PostQuery {
    pub rowid: RowId,
    pub site: DbSite,
    pub id: PostId,
    pub title: String,
    // ...
}
```

**Why rejected:**
- ❌ Field duplication between types
- ❌ Need to convert between types
- ❌ More boilerplate
- ❌ Doesn't solve domain model separation

### Alternative 3: Single Type, Trait-Based Access

```rust
pub struct AnyPostWithEditContext {
    // All fields
}

trait DomainPost {
    fn id(&self) -> PostId;
    fn title(&self) -> &str;
}

trait DbPost: DomainPost {
    fn rowid(&self) -> RowId;
    fn last_fetched_at(&self) -> &str;
}
```

**Why rejected:**
- ❌ Overengineered
- ❌ Runtime overhead
- ❌ Doesn't prevent domain model pollution
- ❌ More complex than wrapper approach

## Type Mapping Strategy

### DbEntity Trait

Domain entity implements `DbEntity`:

```rust
impl DbEntity for AnyPostWithEditContext {
    const TABLE_NAME: &'static str = "posts_edit_context";
}
```

### TryFromDbRow Trait

Wrapper implements `TryFromDbRow`:

```rust
impl TryFromDbRow for DbAnyPostWithEditContext {
    fn try_from_db_row(row: &rusqlite::Row) -> Result<Self> {
        Ok(Self {
            row_id: RowId(row.get(0)?),
            site: DbSite { row_id: RowId(row.get(1)?) },
            post: AnyPostWithEditContext {
                id: PostId(row.get(2)?),
                // ... map other fields
            },
            last_fetched_at: row.get("last_fetched_at")?,
        })
    }
}
```

## Trade-offs

### Advantages

✅ **Clean separation** - Domain model doesn't know about database
✅ **Type safety** - Compiler enforces correct usage
✅ **Flexibility** - Domain entity usable in non-DB contexts
✅ **Clear intent** - Wrapper type signals "this came from DB"
✅ **Easy to extend** - Can add DB metadata without changing domain type

### Disadvantages

❌ **More types** - Need both domain and wrapper types
❌ **Wrapping overhead** - Must wrap/unwrap when needed
❌ **Slightly verbose** - `db_post.post.title` instead of `post.title`

**Mitigation:**
- The benefits outweigh the small verbosity increase
- Type safety prevents errors
- Clearer code structure worth the extra typing
